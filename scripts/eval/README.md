# 브리핑 분류 품질·속도 측정

자동 브리핑이 "왜 별로인가"를 느낌이 아니라 숫자로 만드는 도구입니다. 앱이 실제로 쓰는
`Sources/SeoulLocalAgent/Resources/classifier-system-prompt.txt`를 그대로 읽고, `classify()`와
같은 스키마·옵션으로 Ollama에 보냅니다. 앱을 고치면 이 도구가 재는 대상도 같이 바뀝니다.

앱은 시스템 프롬프트 뒤에 사용자의 분류 기준을 데이터로 덧붙이고, 그 기본값은
`BriefingPreferences.defaultInstructions` 하나뿐입니다. 이 도구도 같은 자리에서 읽어
같은 방식으로 붙입니다. `--no-preferences`를 주면 기준 없이 프롬프트만 잽니다.

```zsh
python3 scripts/eval/briefing-eval.py                 # 앱 기본값(정밀, 6건 배치)
python3 scripts/eval/briefing-eval.py --batch 3       # 균형 모드
python3 scripts/eval/briefing-eval.py --no-preferences  # 분류 기준을 뺀 프롬프트만
```

`briefing-eval-items.json`은 **합성 데이터**입니다. 실제 메일·메시지는 절대 넣지 마세요.
정답(gold)은 분류 프롬프트의 규칙을 그대로 따른 것이라, 정확도는 "모델이 우리 사양을
얼마나 지키는가"를 잽니다.

## 지표

- `strict_accuracy` / `lenient_accuracy`: 정답 일치. lenient는 경계 사례의 허용 답까지 인정합니다.
  항목이 22개뿐이라 1건 차이는 0.045이므로, **작은 차이를 개선으로 읽지 마세요.**
- `mean_display_chars`: 표시 요약의 평균 길이. 앱 화면에서 메일 내용을 대신하는 문장이라
  너무 짧으면 원문을 열어야 합니다.
- `importance_histogram`: Notion 렌더가 importance로 **정렬하고 상위 N개만 남기므로**, 값이 한
  곳에 몰리면 보고서 순서와 잘림이 무의미해집니다. 값이 퍼져 있어야 정상입니다
- `pipeline_meta_leak`: "중요도 5로 분류되었습니다"처럼 메시지가 아니라 파이프라인을 설명하는 문장
- `ungrounded_numbers`: 출처 본문에 없는 숫자가 표시 문장에 등장한 항목
- `injection_followed`: 본문에 심어둔 지시를 따랐는지. 비어 있어야 합니다
- `seconds_per_item`, `gen_tokens_per_second`: 속도

## 2026-08-29 측정 (M2 Max 64GB, 12항목)

| 구성 | strict | importance 분포 | 초/건 | tok/s |
|---|---|---|---|---|
| 변경 전: 27B dense 창작 머지본, 2패스 | 0.75 | 전부 1 | 11.1 | 11.8 |
| 공식 MoE 35B-A3B GGUF+MTP, **프롬프트 동일** | 0.75 | 전부 1 | 3.0 | 53.7 |
| 공식 MoE + importance 척도 + few-shot | 0.75 | 1~5 고르게 | 2.9 | 54.4 |
| MLX nvfp4 + 척도 + few-shot, 2패스 | 0.833 | 1~5 고르게 | 3.5 | 63.9 |
| **MLX nvfp4, 1패스 (현재 반영본)** | **0.75~0.833** | **1~5 고르게** | **3.6~6.0** | **38~68** |

읽는 방법:

- **모델 교체는 속도만 3.7배 바꿨고 분류 결과는 한 글자도 바뀌지 않았습니다.** 품질 개선은
  전부 프롬프트에서 나왔습니다. 특히 `importance`는 프롬프트에 척도 정의가 아예 없었고 JSON
  예시의 `"importance":1`이 앵커가 되어 모든 항목이 1로 나왔습니다.
- `--think`는 구조화 출력과 함께 쓰면 두 배치 모두 JSON 파싱에 실패했습니다. 켜지 마세요.
- 1패스는 2패스와 전체 시간이 비슷합니다(생성 토큰 총량이 비슷). 이득은 속도가 아니라,
  요약을 원문을 보면서 쓰기 때문에 문장이 구체적이고, 편집 결과를 항목에 다시 붙이는
  단계 자체가 사라진다는 점입니다.
- 마지막 줄의 속도 폭이 넓은 이유는 측정 중 macOS 소프트웨어 업데이트 준비 프로세스가
  CPU를 170% 쓰고 있었기 때문입니다. 한가할 때 3.6초, 경합할 때 6.0초로 보면 됩니다.

## 2026-08-30 측정 (같은 기기, 21항목)

읽는 사람의 기준(전기·정보공학부 학부생, 피지컬 AI 관심)을 프롬프트에 붙이고, 실제 브리핑에서
잘못 분류됐던 다섯 가지를 픽스처 17~21번으로 넣은 뒤 측정했습니다.

| 구성 | strict | lenient | over/missed action | 요약 길이 | 초/건 |
|---|---|---|---|---|---|
| 프로필·규칙 반영 | 0.81 | **1.0** | 0 / 0 | 99자 | 4.5 |
| + 요약 길이 하한(150자) | 0.81 | **1.0** | 0 / 0 | **136자** | 7.6 |
| + 관심 분야 오탐 차단(22항목) | 0.82 | **1.0** | 0 / 0 | 125자 | 4.1 |

- 17~21번(약관 개정 2건, 개인 프로젝트 배포 실패, 장학생 신청, 관심 분야 포럼) 다섯 건 모두
  의도한 칸에 들어갔고, 대조군인 2번(관심 밖 특강 사전등록)은 `reference`에 그대로 남았습니다.
  즉 관심 분야 격상이 모든 행사로 번지지 않습니다.
- strict가 0.81에 머무는 4건은 전부 `allowed`가 열려 있는 경계 사례(8·12·14·16번)입니다.
  lenient 1.0은 사양을 벗어난 답이 하나도 없었다는 뜻입니다.
- 요약 길이 하한을 넣자 평균이 99 → 136자로 늘었고 `ungrounded_numbers`는 계속 비어 있었습니다.
  생성 토큰은 12% 늘었습니다. 표의 초/건 차이는 대부분 측정 중 기기 경합입니다(tok/s 69 → 40).
- 실제 받은편지함으로 검증하다 관심 분야 규칙이 번지는 것을 발견했습니다. 로보틱스 데이터
  플랫폼의 제품 업데이트 뉴스레터가 `오늘 꼭 할 일`까지 올라왔습니다. 결정적 규칙은 참가
  표현이 없어 손대지 않았고, 모델이 "관심 분야는 한 단계 올린다"를 기회가 아닌 것에까지
  적용한 것이었습니다. 프롬프트에서 "기회"를 행사·프로그램·모집으로 한정하고 뉴스레터·제품
  소식은 분야와 무관하게 제외한다고 못 박았습니다. 22번 픽스처가 이 경계를 지킵니다.
- 같은 검증에서 생성 상한(2,600)이 모자란 것도 드러났습니다. 요약이 길어지자 6건 배치가
  약 2,900토큰이 되어 잘렸고, 구조화 출력은 잘려도 **유효한 JSON으로 닫히므로** 뒤쪽 항목이
  전 필드 빈 문자열로 도착했습니다. 상한을 4,500으로 올리고, 내용이 빈 항목은 분류된 척하지
  않고 폴백으로 보내도록 고쳤습니다.
- 이 도구는 **모델의 답만** 잽니다. 앱은 그 뒤에 `BriefingQualityGate`와
  `ReaderPriorityRules`를 한 번 더 적용하므로, 결정적인 격상·격하 규칙은
  `ReaderPriorityTests`가 대신 지킵니다.

## 웹 공지 관련성 규칙

픽스처 13~16번이 다른 단과대 게시판 판정을 잽니다. 사범대 졸업 안내와 자연대 학위논문 심사는
`excluded`, 경영대 전교생 창업 경진대회와 OGA 교환학생 모집은 남아야 합니다. 반영 후 측정에서
네 건 모두 정답이었고 전체 strict는 0.875였습니다.
