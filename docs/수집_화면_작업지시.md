# 데이터 수집 화면 — 맥 앱에서 한 것과, 서버에 남은 것

`SO-ARM 101` 한 화면에 물리 리더 텔레옵과 데이터 수집이 같이 있던 것을 갈랐다. 앱 쪽은
끝났고, **화면이 아직 채우지 못하는 칸 셋은 서버가 값을 내주어야 한다.**

관련 문서: [수집용 카메라 작업지시](수집_카메라_작업지시.md).

---

## 1. 맥 앱에서 한 것 (2026-09-05)

로봇 화면이 넷이 되었다.

| 화면 | 하는 일 |
|---|---|
| `SO-ARM 101` | 물리 리더 텔레옵, 진단, 카메라 프리뷰(화질·프레임 고를 수 있음), 토크 해제 |
| `원격 텔레옵` | 3D 가상 리더 (그대로) |
| `데이터 수집` | **새로 만들었다.** 시연을 찍는 것만 |
| `수집 데이터` | 찍은 에피소드 열람 (그대로) |

- `Sources/SeoulLocalAgent/SOArmRecordScreen.swift` — 새 화면. 과제 문장, 한 회 최대
  시간, 시작, 그리고 찍는 동안의 `지금 저장`(⌘⏎)·`다시 찍기`(⇧⌘R)·`수집 종료`(⌘.)와
  화면에 적힌 단축키 안내.
- `SO-ARM 101`에서는 수집 섹션과 확인 시트의 수집 분기를 들어냈고, 로그 상자도 텔레옵
  로그만 보여 준다.
- 수집 화면의 카메라 카드에는 **화질·프레임을 고르는 메뉴가 없다**(`showsSettings`).
  구도를 잡으라고 있는 것이지 고르라고 있는 것이 아니다.
- `일찍 끝내기`는 원래 있었다 — `성공 저장`이 LeRobot의 `right`(=`exit_early`)로 가고
  있었다. 이름이 시간과 관계있다는 것을 말하지 않아 아무도 그렇게 쓰지 않았을 뿐이다.
  버튼 이름을 `지금 저장`으로 바꾸고, 시간 칸 옆에 "**최대**입니다"를 적었다.

### 앱이 일부러 비워 둔 칸

`SOArmEpisodeClock`은 **서버가 회의 시작 시각을 알려 줄 때만** 남은 시간을 센다. 앱이
혼자 세는 길도 있었지만 택하지 않았다: 회 사이 정리 시간(`reset_time_s`)을 앱이 모르고,
시간이 다 되어 끝난 회와 `지금 저장`으로 끝난 회의 경계도 앱에서는 구별되지 않는다.
처음 몇 회는 맞다가 조용히 어긋나고, 어긋난 시계를 보고 손을 떼는 사람이 틀리게 된다.
그래서 값이 없는 동안에는 남은 시간을 적지 않고 왜 못 적는지를 적는다.

`SOArmRecordingRuntime`에는 자리를 이미 만들어 두었다 — `episode_started_at`,
`episode_seconds`, `episode_index`, `loop_hz`. 서버가 그 이름으로 실어 보내면 화면이
저절로 채워진다.

## 2. 서버 Codex에게 줄 프롬프트

```text
저장소: /home/deploy/Project/so-arm-101 (soarm101-console)

맥 앱의 새 `데이터 수집` 화면이 필요로 하는 값 셋을 내주고, 찍은 에피소드의 팔로워
궤적을 돌려주는 엔드포인트를 하나 만든다. RECORDING_PROFILE(640x480@30)과 카메라
역할·calibration·모션 게이트는 건드리지 않는다.

--- 1. 회(에피소드) 진행 상황을 status.json 에 쓴다 ---

src/soarm_console/recording.py 의 _write_status 로 아래 네 값을 내보낸다. 이미 phase,
dataset_name, task, last_control 을 쓰고 있으므로 같은 자리에 붙이면 된다.

    episode_started_at : float  # 지금 회가 시작한 시각 (time.time(), 벽시계)
    episode_seconds    : int    # 한 회의 최대 길이. DatasetRecordConfig.episode_time_s 에
                                # 실제로 들어간 값이지, 앱이 보낸 값을 되돌려 주는 것이 아니다
    episode_index      : int    # 지금 몇 번째 회인가. 0 부터
    loop_hz            : float  # 수집 루프가 실제로 도는 속도 (최근 몇 초 평균)

왜 필요한가: 맥 앱이 남은 시간을 혼자 셀 수 없다. 회 사이 정리 시간(reset_time_s)을
앱이 모르고, 시간이 다 되어 끝난 회와 사용자가 `지금 저장`을 눌러 끝난 회의 경계도
앱에서는 구별되지 않는다. 앱이 흉내 내면 처음 몇 회는 맞다가 조용히 어긋나고, 어긋난
시계를 보고 손을 떼는 사람이 틀리게 된다.

loop_hz 가 특히 중요하다. lerobot_record.record_loop 는 30Hz 를 못 지키면
"Record loop is running slower (...Hz) than the target FPS" 를 **로그에만** 남긴다.
그것이 데이터가 조용히 나빠지는 유일한 경로다 — 데이터셋은 언제나 fps=30 으로 적히고
(DatasetWriter 가 timestamp = frame_index / fps 로 계산한다) 루프가 느려도 파일은
그대로 30 이라고 말한다. 화면이 이 숫자를 보여 줄 수 있어야 한다.

붙이는 방법: 이미 lerobot_record.init_keyboard_listener 를 우리 것으로 갈아 끼우고
있으므로 같은 방식이 쓸 수 있다. lerobot.scripts.lerobot_record.record_loop 를 감싸
(wrap) 호출 직전에 episode_started_at/episode_index 를 쓰고, 루프가 도는 동안
loop_hz 를 주기적으로 갱신하는 쪽이 가장 적게 건드린다. 감싸는 함수가 원본의 시그니처를
그대로 넘겨야 하고, LeRobot 을 올릴 때 시그니처가 바뀌면 곧바로 터지도록 **키워드
인자를 그대로 전달**한다 — 조용히 무시하면 다음 판올림에서 값이 멈춘 채로 남는다.

reset 구간(회와 회 사이)에는 phase 를 "resetting" 으로 쓰고 episode_started_at 을
비운다. 앱이 그 동안 남은 시간을 세면 안 된다.

--- 2. 찍은 에피소드의 팔로워 궤적을 돌려주는 엔드포인트 ---

    GET /api/datasets/{name}/episodes/{episode_index}/trajectory

돌려주는 모양:

    {
      "fps": 30,
      "frames": 412,
      "joints": ["shoulder_pan", "shoulder_lift", ...],
      "state":  [[...6개...], ...],   # observation.state, 프레임 순서대로
      "action": [[...6개...], ...]    # action, 같은 길이
    }

- 데이터는 LeRobot 데이터셋의 parquet 에 있다. src/soarm_console/datasets.py 가 이미
  meta/info.json 을 읽고 경로를 검사하는 방식(NAME_PATTERN, data_root() 밖으로 못 나가게
  하는 resolve 검사)을 그대로 따른다. 새 경로 검사를 따로 쓰지 말고 그 함수들을 쓴다.
- 프레임이 많으면 응답이 커진다. 6개 관절 x 2 x 수천 프레임이면 수백 KB 다. 한 회는
  대개 30초(900프레임)이므로 그대로 돌려주어도 되지만, 프레임 수 상한(예: 20000)을 두고
  넘으면 413 으로 거절한다 — 뒤에 붙는 것이 SSH 터널 너머의 맥이다.
- 관절 이름 순서는 meta/info.json 의 features 에 적힌 순서를 그대로 쓴다. 여기서 정렬을
  다시 하면 앱이 그린 곡선과 실제 관절이 어긋난다.

왜 필요한가: 맥 앱의 `수집 데이터` 화면이 지금은 영상만 재생한다. 시연이 제대로 찍혔는지
보려면 그때 팔이 실제로 어떻게 움직였는지를 같은 시간축에서 봐야 한다 — 영상에서는
멀쩡해 보이는 회가 관절 곡선에서는 튀어 있는 경우가 실제 문제다.

--- 시험 ---
- tests/ 의 기존 방식대로 TestClient 로 궤적 엔드포인트를 부르고, 프레임 수가
  meta 의 값과 같은지, 없는 데이터셋 이름과 없는 회 번호가 404 인지 확인한다.
- 실제로 한 회를 찍고 /api/status 의 recording.runtime 에 위 네 값이 들어오는지,
  reset 구간에서 episode_started_at 이 비는지 본다.
- loop_hz 가 30 언저리인지 본다. 30 을 못 지키면 그것 자체가 따로 고칠 일이다.

끝나면 README 나 해당 문서에 한 문단으로 적고 커밋한다.
```
