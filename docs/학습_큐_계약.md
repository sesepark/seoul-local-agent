# 학습 작업 큐 계약

DGX Spark의 GPU 하나 앞에 줄을 세우는 것. 큐는 **Spark 위의 데몬**(`sparkq`)이 들고 있고,
맥 앱은 SSH 터널 너머로 그 큐를 읽고 고친다. 이 문서는 둘 사이의 계약을 한 번만 적는다.

- **서버(큐 데몬)**: 별도 저장소 **[sesepark/sparkq](https://github.com/sesepark/sparkq)**.
  학습 기계에서 `sehwan_spark@spark:~/sparkq/`에 클론되어 systemd 사용자 서비스로 돈다.
  설치·CLI·작업 종류 만들기 등 **서버 쪽 사용법은 그 저장소의 README**에 있다.
- **맥 앱(이 저장소)**: `Sources/SeoulLocalAgent/SparkQueue.swift`(모델·클라이언트),
  `SparkModel.swift`(화면 상태), `SparkScreen.swift`(화면·설정). 앱은 큐를 읽고 고칠 뿐,
  학습을 띄우거나 순서를 정하는 판단은 하나도 앱에 없다 — 전부 서버의 `sparkq`가 한다.

> **헷갈리지 말 것**: 로봇 파이프라인에는 기계가 둘이다. 팔·카메라가 붙은 **콘솔 서버**
> (`soarm101-console`, 별도 저장소)와, 학습만 맡는 **학습 서버 Spark**(`sparkq`)다. 이 문서와
> `sparkq` 저장소는 **학습 서버** 이야기다. 콘솔 서버는 [원격 텔레옵 계약](원격_텔레옵_프로토콜.md)을 보라.

## 기계가 셋이다

```text
[SO-ARM101 팔 + 카메라 2대]
        │ USB
        ▼
HUB (soarm101-console)              Spark (sparkq)
i7-8700 · GTX 1660                  GB10 · 통합메모리 121GB
녹화 · 텔레옵 · 추론                  학습만
        └────────── tailnet ──────────┘
                    ▲          ▲
                    │          │
              SSH 터널      SSH 터널          맥 앱 (SeoulLocalAgent)
              :8088        :8092
```

데이터셋은 HUB에서 Spark로 **HUB가** 밀어 넣는다(`수집 데이터` 화면의 `학습 서버로 전송`,
콘솔의 `POST /api/spark/datasets/{name}`). 체크포인트를 되찾아 오는 것도 HUB다 — 추론은 팔이
붙어 있는 기계에서 돌기 때문이다. **큐만** 맥이 Spark와 직접 이야기한다.

### 왜 큐만 직결인가

콘솔 서버를 한 번 더 거치면 그 서버가 `systemctl --user restart` 되는 동안 학습 화면이 함께
사라진다. 학습은 밤새 도는 것이고, 그것을 보는 창은 팔이 붙은 기계의 사정과 무관해야 한다.
GPU를 가진 기계가 GPU를 스케줄링하고, 맥은 그 기계만 부른다.

## 신뢰 경계

| 경로 | 어떻게 붙는가 | 인증 |
|---|---|---|
| 맥 앱 → HUB 콘솔 | SSH 로컬 포워딩 → `127.0.0.1:8088` | 조작만 `X-SOARM-Motion-Token` |
| 맥 앱 → Spark 큐 | SSH 로컬 포워딩 → `127.0.0.1:8092` | 없음 — 터널이 곧 경계 |

`sparkq`는 `127.0.0.1`에만 bind한다. LAN에 여는 길은 만들지 않는다. 열쇠는 콘솔 서버의 것과
**따로**다(`spark-tunnel-key`) — 한쪽 접근만 서버에서 회수할 수 있어야 하기 때문이다.

## REST

전부 `/api` 아래. 요청 본문과 응답은 JSON.

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| GET | `/api/status` | 기계 한 줌: GPU 이름·온도·전력·**사용률**, **CPU 사용률**, **통합메모리 사용량**, 디스크, 대기 개수, 일시정지 여부 |
| GET | `/api/kinds` | 걸 수 있는 작업 종류와 그 칸들 |
| GET | `/api/datasets` | Spark에 와 있는 데이터셋 |
| GET | `/api/queue` | 도는 것 1 + 대기열 + 최근 끝난 것 + 큐 밖의 GPU 프로세스 |
| POST | `/api/queue` | `{"kind": ..., "params": {...}}` — 줄 맨 뒤에 세운다 |
| DELETE | `/api/queue/{id}` | 대기면 줄에서 빼고, 도는 중이면 세운다 |
| POST | `/api/queue/{id}/top` | 아직 시작하지 않은 줄에서 맨 앞으로 |
| POST | `/api/queue/pause` | `{"paused": true\|false}` |
| GET | `/api/queue/{id}/log` | 로그 꼬리 400줄 |

사용률은 세 곳에서 온다: GPU는 `nvidia-smi --query-gpu=utilization.gpu`, CPU는 `/proc/stat`을
0.25초 간격으로 두 번 재 그 사이 바쁜 시간의 비율, 메모리는 `/proc/meminfo`의 `MemTotal`과
`MemAvailable`이다. **GB10은 통합메모리라 nvidia-smi의 GPU 전용 메모리는 N/A**이므로, RAM
사용률이 곧 이 기계가 얼마나 찼는지다 — CPU와 GPU가 그 한 메모리를 나눠 쓴다.

거절은 `{"detail": "…"}` 한 줄과 함께 400(값이 잘못됨) 또는 404(그런 작업 없음)로 온다. 앱은
그 문장을 그대로 보여 준다 — 상태 코드만 보여 주면 무엇을 고쳐야 하는지 알 수 없다.

## 작업 종류는 서버가 정한다

`~/sparkq/kinds/*.json` 하나가 종류 하나다. 앱에는 종류가 하나도 박혀 있지 않고, 화면은
서버가 준 칸 명세를 그대로 그린다. **새 실험을 걸 수 있게 하는 데 앱을 고칠 필요가 없다.**

```json
{
  "kind": "lerobot-train",
  "title": "${policy} 학습 · ${dataset}",
  "label": "데이터셋 학습",
  "fields": [
    {"name": "dataset", "label": "데이터셋", "type": "name", "source": "datasets"},
    {"name": "policy", "label": "정책", "type": "enum", "values": ["act", "smolvla"],
     "default": "act", "presets": {"act": {"steps": 100000, "batch_size": 64}}}
  ],
  "derived": [{"name": "run", "template": "${dataset_short}__${policy}__${stamp}"}],
  "session": "train-${run}",
  "progress": "lerobot",
  "run": "…셸 스크립트…"
}
```

칸의 형식은 셋뿐이다.

- `enum` — `values` 안의 값만. `labels`로 사람이 읽는 문장을 붙인다. `presets`가 있으면 고른
  값에 딸린 값들(`steps`, `batch_size`…)이 함께 펼쳐진다.
- `int` — `min`…`max` 사이의 정수.
- `name` — `[A-Za-z0-9._-]{1,80}`. `source: "datasets"`면 목록을 서버에서 가져온다.

**자유 문자열 형식은 없다.** 이 값들은 곧 셸 명령의 일부가 되고, 자유 문자열이 들어가는
순간 이 큐는 원격 셸이 된다. 늘리고 싶으면 종류 파일을 하나 더 만드는 쪽이 맞다.

치환은 `${이름}`이고 `string.Template.safe_substitute`가 한다 — 모르는 이름(`$?`,
`$LD_PRELOAD`)은 건드리지 않고 지나간다. 만들어 낸 명령은 **걸 때** 확정되어 작업 파일에
그대로 적힌다. 자는 동안 도는 것들이므로, 무엇이 돌 것인지 미리 읽을 수 있어야 한다.

## 규칙

- **슬롯은 하나.** GPU가 하나이고, 통합메모리라 두 학습이 겹치면 OOM으로 깨지는 대신 둘 다
  스왑으로 느려진다 — 알아채기 훨씬 어려운 실패다.
- **비선점.** 시작한 작업은 끝나거나 사람이 세울 때까지 둔다. `맨 앞으로`는 아직 시작하지
  않은 줄의 순서만 바꾼다.
- **큐 밖의 작업 위에 올라타지 않는다.** 다음 것을 꺼내는 조건은 `nvidia-smi`의 컴퓨트
  프로세스가 **하나도 없을 때**다. 사람이 터미널에서 직접 띄운 학습도 여기에 걸린다.
- **실패해도 다음으로 간다.** 밤새 돌리는 것이 목적이므로 하나가 깨졌다고 줄 전체가 멈추면
  안 된다. 멈추고 싶으면 화면의 `다음 작업 꺼내지 않기`를 켠다.
- **상태는 전부 디스크에.** `~/.sparkq/` 아래 JSON 파일들이고, 데몬은 그것을 읽어 실행하는
  얇은 층이다. `systemctl --user restart sparkq` 해도 도는 학습은 tmux 안에서 그대로 돌고,
  올라온 데몬이 세션 이름으로 다시 찾아 붙는다.
- **모든 작업의 tmux 세션 이름은 `train-`으로 시작한다.** 데몬이 강제한다.

  학습을 띄우는 문이 둘이기 때문이다 — 이 큐와, HUB 콘솔의 `POST /api/spark/train`(앱의
  `수집 데이터` 화면). 콘솔은 학습을 띄우기 전에 Spark의 tmux 세션 가운데 `train-`으로
  시작하는 것이 있는지만 보고, 있으면 409로 거절한다. 그것이 콘솔이 아는 유일한 "이미 도는
  학습"의 표시다. 큐가 다른 이름을 쓰면 콘솔은 큐의 작업을 **보지 못하고** 그 위에 학습을
  하나 더 띄운다.

  반대 방향은 이미 막혀 있다. 콘솔이 먼저 띄운 학습은 GPU에 컴퓨트 프로세스로 잡히고, 큐는
  그것이 빌 때까지 다음 것을 꺼내지 않는다.

  `lerobot-train`은 여기에 더해 이름이 정확히 `train-<run>`이어야 한다. HUB 콘솔의
  `GET /api/spark/runs`가 그 이름으로 진행을 읽으므로, 바꾸면 `수집 데이터` 화면의
  `학습된 정책`이 조용히 비어 버린다.

## 진행률

종류마다 로그가 다르고, 화면은 한 가지 모양만 읽는다.

| `progress` | 읽는 것 |
|---|---|
| `lerobot` | `step:20K` 줄과 tqdm 막대 중 **큰 쪽**, `loss:` |
| `rsl_rl` | `Learning iteration N/M`, `ETA: H:MM:SS`, `Mean reward:` |
| `none` | 진행률 없음 — 화면은 도는 표시만 그린다 |

`lerobot`에서 둘을 비교하는 이유: `step:` 줄은 `log_freq`(기본 200)마다 나오는데 이 팔의 ACT는
스텝당 2초가 넘어 **첫 줄이 8분 뒤에 나온다.** tqdm은 매 스텝 갱신하므로 늘 더 최근이다.

총량을 모르면 진행률을 지어내지 않는다. 0%에 붙어 있는 막대는 "진행이 없다"로 읽히는데,
실제로는 아직 로그가 말하지 않은 것뿐이다 — 그때는 막대 대신 도는 표시를 쓴다.

## 설치와 운영

```bash
ssh spark
bash ~/sparkq/install.sh          # linger를 켜고 사용자 서비스로 올린다 (sudo 한 번)
systemctl --user status sparkq
sparkq ls                          # 도는 것과 대기열
sparkq add lerobot-train dataset=<이름> policy=act
sparkq add isaac-rl task=Isaac-Lift-Cube-SO101-v0 num_envs=4096 max_iterations=2500
sparkq top <id> / rm <id> / log <id> / pause / resume
```

`loginctl enable-linger`가 **반드시** 켜져 있어야 한다. 없으면 로그아웃과 동시에 사용자
유닛이 전부 죽고, 밤새 도는 것이 목적인 이 큐는 의미가 없어진다.

맥에서는 창을 열지 않고 길 전체를 두드려 볼 수 있다.

```bash
.build/debug/SeoulLocalAgent --spark-check
```

터널이 안 열린 것, 열렸는데 큐가 죽은 것, 큐는 사는데 데이터셋이 없는 것은 화면에서 전부
비슷해 보이지만 고칠 자리가 다르다. 이 명령은 그중 어디서 끊겼는지를 말한다.

## 걸기 전에 알아 둘 것

`act` 프리셋은 10만 스텝이다. 실측(batch 64에서 0.55 step/s)으로 **50시간쯤** 걸린다. 하룻밤에
끝나는 작업이 아니므로, 여러 개를 세워 두면 며칠짜리 줄이 된다. `smolvla`는 2만 스텝이라
훨씬 짧지만 첫 실행은 HF에서 기반 모델을 내려받느라 시작이 늦다.
